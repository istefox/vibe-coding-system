# ADR-0054 — Run the deterministic checks in the target project's CI, fail-closed

- **Status:** Accepted
- **Date:** 2026-07-26
- **Issue:** #108 (ninth feature of PROJECT.md Phase 2)
- **SPEC:** `SPEC.md` / `docs/specs/108-project-ci-deterministic-checks.spec.md`
- **Depends on:** ADR-0046 (#100) for `secret-scan.sh` / `dependency-scan.sh`, ADR-0047 (#101) and
  ADR-0051 (#105) for `weakening-scan.sh` and its `SUSPECT` detectors, ADR-0053 (#107) for
  `interface-check.sh` — which already placed its own step in the template.
- **Closes:** gap **G-11** of `docs/books/INTEGRATION-REPORT-agentic-spec.md` (PARTIAL, P2).
- **Does NOT amend** ADR-0004 / ADR-0034 / ADR-0045: the hooks' fail-open posture stands unchanged.

## Context

The agentic spec states two hook design rules (§10.4): **every hook must work with no agent
present**, and **fail closed**.

This system satisfies the first and deliberately violates the second. Every guardrail is a hook in
`~/.claude/hooks/` wired through `settings.json`, and each fails open by recorded decision —
`stop-gate.sh:4`, `pre-flight-pattern-enforce.sh:5`, `agent-command-scope.sh:11` ("a guardrail …
NOT a sandbox"), `db-backup-guardrail.sh:5`.

That decision is sound and is not reversed here. But the *other* half was never a decision at all:
CI runs the harnesses (`docs-ci.yml:44`) and never runs the gates themselves against a diff, and
`staging/project-templates/ci/ci.yml` contained one substituted `__TEST_CMD__` step. **A project
generated by this system inherits no gate whatsoever in its own CI.**

ADR-0046 §D10 anticipated exactly this and left the note in the template: the reporters exit 0 by
design *so that* CI could later run them fail-closed without modifying them. This is that collection.

## Decision

### D1 — The posture belongs to the caller, not to the script

This is the central idea and it is why no script changes.

The same `secret-scan.sh` is **fail-open** when a hook calls it and **fail-closed** when CI calls
it, because the cost of a false positive is completely different in the two places:

- **Hook, agent present.** A false positive blocks an agent mid-run, often unattended, with a human
  asleep. The failure is expensive and silent. Fail open.
- **CI, no agent present.** A false positive is a red build on a PR that a human is already looking
  at, resolved by reading one log line. The failure is cheap and loud. Fail closed.

So the scripts stay exactly as they are — reporters that always exit 0 and signal through stdout —
and the CI job interprets their output and fails the build. The reporter contract that looked like a
weakness in ADR-0047 is precisely what makes this possible with zero modification.

### D2 — A separate `checks` job, not more steps on `ci`

`ci` is the required status check `set-branch-protection.sh` enforces on `main`. Folding
fail-closed gates into it would mean a secret-scan false positive blocks merges the same way a
failing test does, with no way to distinguish them in the branch-protection UI.

`checks` is its own job, so a repo can require it or not, and a red `checks` reads as "a gate fired"
rather than "the tests broke".

### D3 — The scripts are vendored into the target repo, not fetched

`.claude/scripts/` in the target repo, committed. Not downloaded at CI time, not `git clone`d from
this repository.

Three reasons, in order of weight: a CI run that reaches the network to fetch its own security
gates has made those gates depend on an external service being up and honest; a vendored copy is
pinned, so a gate cannot change under a project without a visible diff; and a committed script is
reviewable in the PR that introduced it.

The cost is drift — a vendored copy goes stale relative to this repository. Accepted, and it is the
same trade `sync-to-claude.sh` already makes for `~/.claude`. A refresh command is provided; nothing
runs it automatically.

### D4 — Vendoring is explicit, and inertness stays visible

A `vendor-checks.sh` copies the current scripts into a target repo's `.claude/scripts/`. Until it is
run, every gate step stays inert — guarded by `[ -x … ]` — and **prints a skip notice**, exactly as
ADR-0046's template comment already does.

Silent inertness is the failure mode this codebase keeps rediscovering: ADR-0043's undeployed fix
that nothing reported, ADR-0046's awk-interval guard, ADR-0044's harness that validated the deployed
copy while the fix sat in staging. A gate that is not installed must say so in the log, because a
skipped step and a passing step look identical otherwise.

### D5 — Which findings fail the build, and which only print

Fail-closed does not mean everything blocks. The split follows the evidence-quality axis this
roadmap has now used three times (ADR-0048 §D7, ADR-0051 §D2, ADR-0053 §D2):

- **Fail the build:** `SECRET` findings, `WEAKENED` findings, a broken protected interface
  (`interface-check.sh` exit 3). All mechanical.
- **Print only:** `SUSPECT` findings and dependency-diff notes. Heuristics — ADR-0051 measured
  `literal-assertion-added` at 25% precision, and a gate at that rate would be disabled within a
  week.

A `checks` job that fires on heuristics is a `checks` job someone adds to the ignore list.

### D6 — Each call site states the script's contract, again

Two reporters (`secret-scan.sh`, `weakening-scan.sh`, `dependency-scan.sh`) and one checker
(`interface-check.sh`) are invoked in the same YAML file with opposite idioms. The reporter trap is
restated inline: never `[ -n "$out" ]` (true even on `CLEAN`), never `grep -c … || echo 0` (two-line
`0\n0`; `|| true` is the fix — issue #100 hit this exact bug).

ADR-0053 §D3 recorded that this confusion has now been written down in three consecutive ADRs and
that prose is not fixing it. This is the fourth. The residual stands and belongs in its own issue.

## Alternatives rejected

- **A1 — Change the scripts to exit non-zero on findings.** Rejected under §D1: it would break every
  hook call site, which needs fail-open, to serve the CI call site, which needs fail-closed. The
  posture is the caller's.
- **A2 — Fetch the scripts at CI time from this repository.** Rejected under §D3: makes a project's
  security gates depend on an external service, unpinned and unreviewable.
- **A3 — Add the gates as steps on the existing `ci` job.** Rejected under §D2: conflates "a gate
  fired" with "the tests broke" in branch protection.
- **A4 — Fail the build on `SUSPECT` findings too.** Rejected under §D5 on measured precision.
- **A5 — Vendor automatically during project generation.** Rejected: it would put executable files
  into a repo without the operator's knowledge. §D4's explicit command plus a visible skip notice is
  the honest version.

## Consequences

### Positive

- A generated project gets real pre-merge gates for the first time; today it gets none.
- The spec's "fail closed" rule is satisfied where it is safe to satisfy it, without reversing the
  fail-open decision where it is not.
- Zero changes to any existing script, so no hook call site is affected.

### Negative, stated plainly

- **Vendored copies drift.** A refresh command exists; nothing enforces its use, and a project can
  sit on a year-old secret-scan without noticing.
- **Inert until vendored** (§D4). The skip notice makes that visible, but the feature does nothing
  on the day it merges — the same shape as ADR-0052 §D1 and ADR-0053.
- **The fail-open/fail-closed split now lives in two places** for the same script, and only prose
  connects them. Someone will eventually "fix" the inconsistency in the wrong direction; §D1 is
  written at length so that reader has something to read.
- Fourth restatement of the reporter/checker contract confusion (§D6), still unenforced.
