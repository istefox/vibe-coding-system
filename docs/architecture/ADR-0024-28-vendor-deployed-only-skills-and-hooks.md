## 1. Context

`vibe-coding-system` is a blueprint repository: `docs/vibe-coding-system.md` is the specification, but the
*executable* agentic system it describes — sub-agents, skills, hooks — lives and runs from `~/.claude`, outside
git entirely. `staging/` plus `staging/sync-to-claude.sh` (ADR-0022) is the one existing bridge: a small,
manually-reviewed tree that mirrors a subset of `~/.claude` and can push fixes back out via a PAIRS table
(`src|dst`, dry-run by default). Today that bridge covers roughly 15 files. Audit finding 3.38 flags the gap
directly: a machine loss (or an accidental `rm -rf ~/.claude`) would silently erase the entire multi-agent
system — 17 skills' worth of `SKILL.md` + scripts + tests, and 12 more hooks — with no recovery copy anywhere.

This is issue #28, the **first** of a 13-issue audit-fix roadmap (#28-#40, see the Project Roadmap). It is
explicitly the enabler: every other issue in the roadmap (#29 refreshes stale copies, #33/#34/#35/#36/#37/#38/#39/#40
patch specific vendored files) assumes the file it wants to fix already exists in `staging/` at a specific,
predictable path. Five sibling specs were already generated by the Phase P prep sweep (ADR-0023) and were read in
full before writing this ADR; three make that dependency explicit and non-negotiable:

- Spec #38 (hook hardening): "hooks vendored into `staging/plugin/scripts/` by issue #28" — and it edits
  `pre-flight-pattern-enforce.sh` and "update[s] the two greps in the pattern-enforce test", meaning the legacy
  `pre-flight-pattern-enforce.sh` test harness (see below) must land in `staging/` at a stable, discoverable path.
- Spec #37 (vibe-status): scope is explicitly "under `staging/plugin/skills/vibe-status/`, vendored by issue #28,
  **except** `INTEGRATION.md` which already exists in staging" — i.e. #37 expects `SKILL.md`, `scripts/aggregate.sh`,
  `scripts/harness-runner.sh`, `tests/run-tests.sh` to already be present, added *alongside* the pre-existing,
  unrelated `INTEGRATION.md` / `scripts/chain-memory-section.sh` (an ADR-0021 artifact never wired or vendored
  before now).
- Spec #29 (refresh stale copies) explicitly owns a *different*, non-overlapping set (`staging/plugin/agents/`,
  seven repo-native `SKILL.md` files, `user/` config, `goal-loop`/`research-prompt` PAIRS) — confirming the 9
  skills already in `staging/plugin/skills/` that are *not* in this issue's list (`adr-writer`, `claude-md-generator`,
  `code-review-checklist`, `commit`, `fastapi-react-vibe`, `interview-driver`, `project-conductor`, `spec-from-issue`,
  `swift-vibe`) are a separate, already-repo-native category this issue must not touch.

Reading the actual deployed tree (`~/.claude`, authorized read-only for this feature) before planning surfaced four
structural facts the SPEC does not spell out, each of which forces a real decision:

1. **Two incompatible hook-test conventions coexist under `~/.claude/hooks/tests/`.** Four files
   (`phase1.test.sh`, `prep.test.sh`, `hook-probe.test.sh`, `hook-verify-workflow.test.sh` — already vendored by
   ADR-0016/ADR-0022) are hermetic: they build fixtures under a tempdir and invoke the script under test via a
   path relative to the repo, so they run identically in `staging/` or deployed. Three more
   (`db-backup-guardrail.sh`, `pre-flight-pattern-enforce.sh`, `run-hook-tests.sh` — none vendored yet, all in
   this issue's scope) hardcode `HOOK="$HOME/.claude/hooks/<name>.sh"`: they always exercise the *deployed*
   script, never a vendored one, and `run-hook-tests.sh` additionally exercises `backup-before-deploy.sh`
   (Task 7), which this issue is explicitly told not to vendor (retired by #38).
2. **`~/.claude/skills/concept-to-code/`, copied naively as "the full directory," would create a duplicate
   source of truth.** It contains `scripts/hook-verify-workflow.sh` — already vendored at the flat path
   `staging/plugin/scripts/hook-verify-workflow.sh` under an existing, unmodified ADR-0016 PAIRS entry — plus
   `SKILL.md.bak-2026-07-10` (excluded by SPEC's own `*.bak-*` rule) and `memory/agent-notes/architect.md`, a
   directory not named in SPEC's subdir list (`SKILL.md, scripts/, tests/, references/, assets/`) and which is
   accumulated runtime state (agent notes written during real chain runs), not shipped skill code.
3. **`sync-to-claude.sh`'s dry-run/apply contract is explicitly frozen** ("`API / Interfaces`: dry-run/apply
   contract unchanged; only the PAIRS table grows" — SPEC, verbatim). Any fix requiring new script logic (directory
   recursion, path rewriting) is off the table by SPEC's own words, not just by convention.
4. **The local test command and CI use two different mechanisms over the same directory.** `.claude/test-cmd`
   (`for t in staging/plugin/scripts/tests/*.test.sh; do bash "$t" || exit 1; done`) is a glob — any new
   `*.test.sh` file is picked up automatically. `.github/workflows/docs-ci.yml`'s `shell-tests` job instead
   hardcodes `for t in phase1 prep hook-probe hook-verify-workflow`, an explicit named list — a new `.test.sh`
   file is invisible to CI until that list is edited by hand.

## 2. Decision

Vendor the SPEC-listed files verbatim into `staging/`, extend the PAIRS table with one entry per vendored file
(additive only), and resolve the four structural facts above as follows.

### 2.1 Vendor scope, directory layout, and exclusions

- Hooks land flat in `staging/plugin/scripts/<name>.sh` (mirrors the existing convention for
  `auto-format.sh`, `nightly-guard.sh`, etc.). Skills land at `staging/plugin/skills/<name>/<relpath>`,
  copying only the subdirectories SPEC names (`SKILL.md`, `scripts/`, `tests/`, `references/`, `assets/`) —
  never `memory/` or any other undocumented subdirectory found alongside them.
- `~/.claude/skills/concept-to-code/scripts/hook-verify-workflow.sh` is **excluded** from the concept-to-code
  copy: it already has a canonical staging home (`staging/plugin/scripts/hook-verify-workflow.sh`, ADR-0016,
  unmodified). `SKILL.md.bak-2026-07-10` and `memory/agent-notes/architect.md` are excluded per the rules above.
- `staging/plugin/skills/vibe-status/` already contains `INTEGRATION.md` and `scripts/chain-memory-section.sh`
  (unrelated ADR-0021 artifacts, never deployed under those names). This issue only **adds** `SKILL.md`,
  `scripts/aggregate.sh`, `scripts/harness-runner.sh`, `tests/run-tests.sh` to that directory; it does not
  touch, wire, or add a PAIRS entry for the two pre-existing files (that is issue #37's job, confirmed by its
  own spec).
- No file under `~/.claude` is read for anything other than `cp`; no hook wiring (`~/.claude/settings.json`,
  `staging/plugin/hooks/hooks.json`) is touched. These 12 hooks are already deployed and already wired via the
  classic `~/.claude/hooks/` + `settings.json` mechanism; vendoring changes nothing about how they run.

### 2.2 PAIRS: one entry per file, strictly additive

Every vendored file gets exactly one new PAIRS line, `plugin/<relpath>|<deployed-relpath>`, following the
transformation already established by the existing 15 entries (`plugin/scripts/X` ↔ `hooks/X`,
`plugin/skills/X/Y` ↔ `skills/X/Y`, `plugin/scripts/tests/X` ↔ `hooks/tests/X`). No existing PAIRS line is
edited, reordered, or removed. `sync-to-claude.sh`'s copy/diff logic is not touched.

### 2.3 Legacy (`$HOME`-coupled) hook tests: vendor byte-identical, keep their original names, do not wire into
the automated suite

`db-backup-guardrail.sh`, `pre-flight-pattern-enforce.sh`, and `run-hook-tests.sh` land in
`staging/plugin/scripts/tests/` under their **original, unrenamed** names (content and name both untouched).
Because they do not end in `.test.sh`, neither the local glob nor CI's explicit list picks them up — this is
deliberate, not an oversight: their `$HOME/.claude/hooks/...` dependency makes them fail hard on any CI runner
(no `~/.claude` on `ubuntu-latest`) and, even locally, they would silently validate whatever happens to be
deployed rather than the staged content being vendored, defeating the point of a patchable source. They still
get PAIRS entries (`plugin/scripts/tests/db-backup-guardrail.sh|hooks/tests/db-backup-guardrail.sh`, etc.) so a
future repo-side fix (spec #38 explicitly plans one, to the pattern-enforce test) can still reach deployment.
Note for the coder: `plugin/scripts/db-backup-guardrail.sh` (the hook) and
`plugin/scripts/tests/db-backup-guardrail.sh` (its legacy test) share a basename in different directories —
this mirrors the deployed layout exactly and is not a duplication bug.

### 2.4 New completeness harness: structural check only, wired into both the local glob and CI's explicit list

A new `staging/plugin/scripts/tests/pairs-completeness.test.sh` parses the PAIRS block out of
`sync-to-claude.sh` (the same `src|dst` format the script itself reads) and asserts every `src` exists as a
file under `staging/`. This is hermetic (no `~/.claude` dependency) and runs identically in CI and locally, so
it is added to `.claude/test-cmd`'s glob automatically (no edit needed there) and appended to
`docs-ci.yml`'s explicit list (`... hook-verify-workflow pairs-completeness`). It does **not** assert byte-identity
against `~/.claude` — see §3.4 for why that check is deliberately excluded from the permanent suite. It is not
itself vendored to `~/.claude` (its logic is meaningless outside a repo checkout; it gets no PAIRS entry).

### 2.5 Markdownlint

SPEC flags this as a real possibility, not a certainty: run `npx --yes markdownlint-cli2 "staging/plugin/skills/**/*.md"`
after all skill content lands (Task 7 of the implementation plan) and only if it reports failures, add
`"staging/plugin/skills"` to the `ignores` array in `.markdownlint-cli2.jsonc` (same bare-path style already used
for `"docs/superpowers"` in that file; verified against the upstream markdownlint-cli2 docs that `ignores` takes
glob/path expressions applied at enumeration time — a bare directory path excludes the whole subtree, matching
the existing entry's proven behavior). No pre-emptive config edit without an observed failure.

## 3. Alternatives considered

### 3.1 Legacy hook-test handling

**Chosen:** vendor `db-backup-guardrail.sh`, `pre-flight-pattern-enforce.sh`, `run-hook-tests.sh` byte-identical,
original names, not wired into any automated suite (§2.3).

- **Alternative A — rename to `*.test.sh` and let the existing glob pick them up.** Rejected. Their content
  hardcodes `$HOME/.claude/hooks/...`; on a GitHub Actions `ubuntu-latest` runner (no `~/.claude`) they would
  fail with "No such file or directory," directly regressing SPEC's own success criterion ("existing docs-ci
  harnesses stay green") as a side effect of this very issue. Locally, renaming without fixing the path would
  make the test validate whatever is *deployed* on the machine that runs it, not the *staged* content this issue
  exists to make patchable — a staging-side fix to, say, `pre-flight-pattern-enforce.sh` would pass or fail this
  test based on an unrelated, unsynced deployed copy, which is actively misleading.
- **Alternative B — rewrite the hardcoded `$HOME/.claude/hooks` path to point at the sibling staging copy, making
  them hermetic, then wire into the glob.** Rejected. This is a content edit beyond a faithful copy, in direct
  conflict with SPEC's "byte-identical...at vendoring time" requirement and its explicit exclusion "Fixing defects
  in the vendored files (that is the rest of the roadmap)." It also does not have an obvious answer for
  `run-hook-tests.sh`'s Task 7, which exercises `backup-before-deploy.sh` — a file this same issue is told not to
  vendor; a hermetic rewrite would have to invent a decision about a reference to a file that no longer exists in
  the vendored tree, which is exactly the kind of defect-adjacent scope a dedicated future issue should own, not a
  vendoring pass.

### 3.2 PAIRS granularity

**Chosen:** one PAIRS entry per file, matching SPEC's literal instruction and the existing 15-entry precedent
(§2.2).

- **Alternative — directory-level PAIRS entries** (e.g. `plugin/skills/concept-to-code/|skills/concept-to-code/`)
  with `sync-to-claude.sh` taught to recurse. Rejected. It requires changing the script's copy/diff logic (a new
  "is this a directory?" branch), which SPEC explicitly forbids ("dry-run/apply contract unchanged; only the
  PAIRS table grows"). It also degrades the per-file diff UX the script currently gives on `--apply` (a directory
  diff is materially harder to review than "this one file changed"), which matters for the exact workflow this
  issue is meant to enable: future issues making a small fix to one vendored file and syncing just that file out.

### 3.3 Handling the concept-to-code duplicate and runtime-state directory

**Chosen:** exclude `scripts/hook-verify-workflow.sh` (already vendored elsewhere) and `memory/agent-notes/`
(runtime state, not in SPEC's subdir list) from the concept-to-code copy (§2.1).

- **Alternative A — copy everything verbatim, including a second copy of `hook-verify-workflow.sh` nested under
  the skill and the `memory/` directory.** Rejected. Two staging paths with identical content and (if both got
  PAIRS entries) the same deployed destination is an undefined situation for `sync-to-claude.sh` — the script has
  no defined behavior for two entries sharing a `dst`, and even without a second PAIRS entry, two on-disk copies
  of the same file will drift the first time either one is edited by a future issue, defeating the "single
  versioned source of truth" goal stated in SPEC's own objective 3. Vendoring `memory/agent-notes/architect.md`
  additionally ships accumulated, machine-local agent working notes as if they were shipped skill code — a
  category error, and arguably content that should not be in a "clean" vendored snapshot at all.
- **Alternative B — treat this as a chance to clean up: move the existing flat `hook-verify-workflow.sh` PAIRS
  entry to the new nested skill path and delete the old one.** Rejected. This retroactively restructures an
  already-shipped ADR-0016 artifact, which exceeds this issue's explicitly additive-only scope ("only the PAIRS
  table grows") and risks a regression to anything currently depending on the flat path (`docs-ci.yml`'s
  `shell-tests` job runs `hook-verify-workflow.test.sh`, whose fixtures reference the script under test by its
  current path). A restructure like this deserves its own reviewed, dedicated change — not a side effect of a
  vendoring issue with an explicit "no restructuring" constraint from its own SPEC.

### 3.4 Scope of the new completeness test

**Chosen:** `pairs-completeness.test.sh` asserts structural completeness only (every PAIRS `src` exists in
staging); the one-time "zero diff against currently-deployed" verification from SPEC's success criteria is
performed manually, once, via the existing `sync-to-claude.sh` dry-run during implementation, and reported in
the coder's checkpoint — not baked into the permanent automated suite (§2.4).

- **Alternative — add a permanent test asserting byte-identity between every vendored file and its
  `$HOME/.claude` counterpart.** Rejected for two independent reasons, either one sufficient on its own. First,
  it cannot run in GitHub Actions CI at all (`ubuntu-latest` has no `~/.claude`), so it would need a permanent
  CI-only skip branch, which makes it a test that only ever half-runs — dead weight in the one environment meant
  to catch regressions automatically. Second, and more importantly, it would produce **false failures by
  design** the moment the audit-fix roadmap does its job: issues #29-#40 (this very issue's stated reason for
  existing, per SPEC objective 3) will edit staging copies and only sync them out to `~/.claude` later, by
  explicit human action. A permanent "must match deployed" assertion would turn red the instant a future issue
  correctly gets ahead of deployment — punishing the intended workflow, not protecting it.

## 4. Consequences

### Positive

- Closes audit finding 3.38: the ~90 files this issue adds (12 hooks, 3 legacy hook tests, 75 skill files across
  16 skills/subsets) go from "exists only on one machine, in a directory git does not track" to "committed,
  reviewable, recoverable from any clone." Combined with the 15 files already tracked, roughly 105 of the
  deployed executable surface's files now have a repo-tracked recovery copy.
- Directly unblocks the rest of the roadmap: issues #33, #37, #38 (read in full while planning this ADR) each
  name a specific file this issue vendors and assume it is already in `staging/` at a specific path; #29 is
  confirmed non-overlapping (different files, different problem — staleness, not absence).
- `pairs-completeness.test.sh` is a permanent, near-zero-maintenance guard against future PAIRS/file drift
  (an entry added without its file, or a file deleted without removing its entry) — valuable for every future
  issue that touches PAIRS, not just this one.
- Zero behavioral change to the live, currently-deployed system: this is a pure additive copy into a docs/tooling
  repo; no hook wiring, no `settings.json`, no `hooks.json`, and no file under `~/.claude` is touched.
- The ADR records, for the first time, the split between "hermetic, staging-testable" hook tests and
  "deployment-coupled" legacy hook tests — a distinction that was previously implicit (discoverable only by
  reading file contents) and that future issues (starting with #38, which edits one of the legacy tests) can now
  cite instead of rediscovering.

### Negative

- The diff this issue produces is large (roughly 90 new files, ~90 new PAIRS lines) and mechanical, which is
  harder to hand-review line-by-line than a typical small feature PR; review has to lean on
  `pairs-completeness.test.sh` plus a directory listing rather than reading every vendored file closely. This
  risk is mitigated by the content being copied verbatim from a live, already-working deployment rather than
  newly authored — the risk surface is "faithful copying," not "new logic bugs."
- The three legacy hook tests remain CI-dark even after vendoring: a future regression in
  `db-backup-guardrail.sh`, `pre-flight-pattern-enforce.sh`, or any of the small hooks only covered by
  `run-hook-tests.sh` (`ensure-state-dir.sh`, `mark-dirty.sh`, `reset-gate-counter.sh`, `stop-gate.sh`, and
  others) is caught only by a human running them against a real `~/.claude` locally, never by this repo's CI.
  This is a carried-over pre-existing gap (it is exactly as true today, before vendoring), not a new one, but
  vendoring makes it visible and documented rather than fixing it — a natural candidate for a future issue to
  make these three tests hermetic, out of scope here.
- `staging/plugin/skills/vibe-status/` now holds two unrelated concerns side by side: the pre-existing
  `INTEGRATION.md` / `chain-memory-section.sh` (ADR-0021, staged 2026-06-22, never deployed) and the newly
  vendored `SKILL.md` / `scripts/aggregate.sh` / `scripts/harness-runner.sh` / `tests/run-tests.sh`. Slightly less
  clean than a fresh directory, though this exactly mirrors deployment reality (the deployed skill has no
  `INTEGRATION.md` or `chain-memory-section.sh` under those names) so there is no PAIRS conflict, just a minor
  readability cost until issue #37 wires the two together.
- `sync-to-claude.sh` grows from 15 to roughly 105 PAIRS lines and from ~70 to ~160 lines of script. Still a
  single flat, readable bash file, but future issues extending it further should watch for the table becoming
  unwieldy as a monolithic block — not a problem yet, worth tracking.

### Neutral

- Whether `.markdownlint-cli2.jsonc` needs a scoped ignore for `staging/plugin/skills` is determined by an actual
  lint run during implementation (Task 7), not decided upfront here — the outcome depends on the literal vendored
  Markdown content, not a design choice this ADR needs to make.
- `concept-to-code`'s runtime-generated `memory/agent-notes/` directory is now explicitly and permanently excluded
  from vendoring by documented convention, so a future "are we missing files?" audit does not flag it as an
  oversight.
- This ADR does not change how any hook is wired (`settings.json` PreToolUse/PostToolUse entries, or the plugin
  `hooks.json` manifest) — it only adds a recovery/patch copy under `staging/`, consistent with the existing
  `sync-to-claude.sh` "MANUAL STEP" precedent (already used for `nightly-guard.sh`'s wiring) for anything touching
  how a hook actually runs.
